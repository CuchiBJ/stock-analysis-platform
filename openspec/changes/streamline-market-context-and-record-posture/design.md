## Context
PostureExplanation ocupa más de una pantalla antes del resumen diario; SectorEvolution renderiza todos los gráficos. SessionChanges fuerza postura a unavailable. El motor calcula la decisión actual y analyze_as_of reconstruye; esa reconstrucción no equivale a una decisión emitida. Los endpoints current/overview están protegidos y get_db cierra sin autocommit.

## Goals / Non-Goals
**Goals:** Escaneo compacto, evidencia accesible, persistencia factual desde la implantación.
**Non-Goals:** Cambiar decisiones, generar recomendaciones, reescribir Dashboard, reconstruir historia previa, ejecutar acciones productivas.

## Decisions
1. PostureExplanation mantiene visibles estado/instrucción/model.summary, model.currentDamage y continuidad. Un details cerrado “Evidencia y condiciones de reparación” contiene las filas nivel/dirección/memoria, ambas listas de gates y notas; auditoría original permanece disponible dentro. Sin truncar evidencia ni cambiar helper de política. Avisos de datos faltantes/daño actual permanecen visibles. Objetivo desktop960px: estado+síntesis <=400px con fixture FUERA normal.
2. SectorEvolution usa tabla semántica compacta (máximo6 columnas: sector, tasa máximos actual, tasa mínimos actual, delta máximos, delta mínimos, cobertura actual). Un caption visible fecha las tasas/cobertura y el intervalo de deltas; encabezados cortos evitan repetir y partir fechas en cada columna. Cada nombre es botón con aria-expanded/aria-controls que abre un único panel bajo la tabla; seleccionarlo otra vez lo cierra. Panel conserva sparklines0..100%, cobertura histórica, advertencias y listado fechado. Selección por nombre estable tras refresh; si desaparece se cierra. Sin sector seleccionado por defecto. Tabla dentro overflow-x-auto para anchos reducidos. Concentración, metodología y estados pending/error/legacy permanecen.
3. Persistencia global sin datos de usuario: modelo MarketPostureRecord, clave primaria session_date; state String16 con enum/check estados conocidos, payload JSON con instruction/reasons/unlock/policy completos, recorded_at UTC timezone-aware. Una fila por sesión representa la ÚLTIMA postura observada, no cierre certificado ni primera emisión. Guardar en current/overview después de preparar toda la respuesta; no usar analyze_as_of. Repetición actualiza misma fila. Upsert PostgreSQL atómico con condición recorded_at anterior; esto evita que una escritura antigua sobrescriba una nueva. Prueba SQLite o SQLAlchemy testdouble sin producción. Modelo registrado en Alembic, migración sobre head e5f6a7b8c9d0; downgrade quita sólo tabla nueva.
4. Repositorio nuevo contiene upsert/lectura; servicio nuevo serializa y controla transacción y commit explícito. No se necesita savepoint porque ambos endpoints sólo han leído antes del registro. Un fallo SQLAlchemy de persistencia/consulta hace rollback, log sin payload y devuelve status unavailable sin impedir contexto general. No capturar excepciones de programación genéricas. No persistir ctx.posture ausente/estado inválido; historia unavailable. El servicio se llama también en respuestas que reutilizan cache de motor: se registra la postura realmente devuelta. Dashboard /current mantiene exactamente el mismo cuerpo JSON.
5. Contrato compartido overview aditivo opcional frontend: posture_history: {status:'available'|'unavailable', records:[{date:'YYYY-MM-DD',state:'FUERA'|'DEFENSIVO'|'SELECTIVO'|'NORMAL'|'AGRESIVO',instruction:string,recorded_at:ISO-UTC}]}. Leer siempre as_of; agregar spy.previous_date sólo si es válida, estrictamente anterior y spy.date===as_of. No sustituir fechas ni usar snapshot futuro. No cachear historia junto con evidence TTL; consultar después de guardar. Con error records=[]; con éxito puede faltar la sesión previa. Payload completo se conserva en DB, respuesta mínima. No crear endpoint nuevo.
6. Frontend agrega tipo optional y posturaChange helper. Exige status available, exactamente una fila válida por cada fecha referencia, timestamps ISO UTC (Z o +00:00), estados conocidos, current record.state===overview.context.posture.state. Si faltan fechas/filas o hay duplicados/inconsistencia => unavailable con motivo, nunca neutral. Orden por permisividad FUERA<DEFENSIVO<SELECTIVO<NORMAL<AGRESIVO; etiquetas “Más restrictiva”, “Menos restrictiva” o “Sin cambio”, evidencia estados+fechas+hora de registro. No asociar menos restricción a recomendación: texto especifica registro observado, no cierre oficial. Mantener ranking deterioros primero y fallback API anterior.

## Risks / Trade-offs
- Sin visitas no hay emisiones registradas: comparación empieza cuando existen registros exactos; explicitar inicio progresivo y no backfill.
- Persistencia en GET representa telemetría del resultado entregado, global e idempotente por sesión; requiere migración antes de captura. Si falta tabla, contexto funciona y comparación indica unavailable.
- Registro global independiente de identidad porque política/contexto es de mercado; no añadir usuario ni datos de cartera.
- Datos intradía pueden cambiar dentro de sesión: usar “última postura registrada por sesión” y timestamp; no presentar como cierre.
- Tabla resume seis columnas y gráficos sólo del seleccionado para reducir longitud sin ocultar deterioro.

## Migration Plan
Crear migración y verificar upgrade/downgrade en DB desechable o generación SQL offline. No aplicar a producción. Frontend tolera backend anterior. Despliegue posterior debe aplicar migración antes o junto con código; observación histórica inicia en ese momento.
